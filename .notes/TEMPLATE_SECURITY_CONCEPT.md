# Архитектурная концепция: Переиспользуемый шаблон безопасности данных (Security & IAM Chassis)

## 1. Введение и назначение концепции

При разработке аналитических и прикладных платформ инженеры данных и бэкенд-разработчики часто сталкиваются с дублированием инфраструктурного кода авторизации. В каждом новом проекте приходится заново настраивать:
- механизмы аутентификации пользователей и SSO;
- правила обмена авторизационными кодами без риска перехвата;
- библиотеки валидации асимметричных цифровых подписей токенов;
- фильтрацию SQL/NoSQL-выборок на основе субъекта токена.

**Цель шаблона:**
Выделить проверенный контур безопасности (Keycloak + OAuth 2.0 PKCE + JWT RS256 Verification + Data Isolation Filter) в независимый от прикладной специфики каркас (Security Chassis). 

Этот шаблон позволяет развернуть защищенный периметр вокруг **любой целевой базы данных** (PostgreSQL, ClickHouse, MongoDB, Redis) или API без написания механизмов защиты с нуля.

## 2. Разделение зон ответственности (Что входит в шаблон, а что заменяется)

Главный архитектурный принцип шаблона — строгое отделение **защитного периметра** от **бизнес-логики и хранилища данных**.


```

┌────────────────────────────────────────────────────────────────────────┐
│                   НЕИЗМЕНЯЕМЫЙ ШАБЛОН БЕЗОПАСНОСТИ                     │
│                                                                        │
│   [Пользователь / Браузер]                                             │
│              │                                                         │
│              ▼ (OAuth 2.0 PKCE S256)                                   │
│   [Keycloak IdP (Realm Template)]                                      │
│              │                                                         │
│              ▼ (JWT RS256)                                             │
│   [Frontend Auth Client (React Keycloak Provider)]                     │
│              │                                                         │
│              ▼ (Bearer )                                               │
│   [Security Proxy / Reporting API Middleware]                          │
│   - Валидация подписи через JWKS (RS256)                               │
│   - Проверка срока действия (exp)                                      │
│   - Извлечение ID субъекта: user_id = token.get("sub")                 │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                    Точка интеграции (Коннектор)
                                    │
┌───────────────────────────────────▼────────────────────────────────────┐
│                  ЗАМЕНЯЕМЫЙ ЦЕЛЕВОЙ КОНТУР ДАННЫХ                      │
│                                                                        │
│   Любая целевая база данных / Хранилище:                               │
│   - ClickHouse (витрина отчетов MergeTree)                             │
│   - PostgreSQL (транзакционные профили)                                │
│   - MongoDB / DocumentDB                                               │
│                                                                        │
│   Правило выполнения запроса:                                          │
│   SELECT * FROM target_table WHERE owner_id = :user_id;                │
└────────────────────────────────────────────────────────────────────────┘

```

### 2.1. Входит в состав шаблона (Неизменяемое ядро):
1. **Провайдер аутентификации (Identity Provider):**
   - Контейнеры `keycloak` и `keycloak_db`.
   - Шаблон конфигурации `realm-template.json` с предустановленными параметрами:
     * Обязательное требование PKCE: `pkce.code.challenge.method: S256`.
     * Отключение прямого парольного входа: `directAccessGrantsEnabled: false`.
     * Базовые роли и настройки маппинга токенов.
2. **Клиентский модуль авторизации (Frontend Auth Skeleton):**
   - Минимальный SPA-клиент (React/TypeScript), инкапсулирующий работу с `keycloak-js`.
   - Настроенная инициализация с параметром `pkceMethod: 'S256'`.
   - Автоматический перехват HTTP-вызовов и подстановка заголовка `Authorization: Bearer <access_token>`.
3. **Защитный шлюз доступа / Модуль безопасности API (Security Middleware):**
   - Легковесный модуль на Python (FastAPI) с автономной валидацией токенов.
   - Механизм кэширования публичных ключей Keycloak (`/protocol/openid-connect/certs`) для верификации асимметричной подписи по алгоритму `RS256`.
   - Обработчик извлечения контекста пользователя (`get_current_user`), отдающий проверенный `sub` / `preferred_username` и перечень ролей.
4. **Инфраструктурная оркестрация:**
   - Базовый `docker-compose.yaml`, связывающий сервисы в единую сеть `security_net` с изоляцией внутренних портов.

### 2.2. Заменяется под конкретный проект (Целевой контур):
1. **Хранилище данных:**
   - В текущем проекте: колоночная СУБД **ClickHouse** с таблицей `prosthetic_reports_mart`.
   - В другом проекте: реляционная **PostgreSQL**, документоориентированная **MongoDB** или аналитическое озеро данных.
2. **ETL-контур и оркестрация:**
   - В текущем проекте: **Apache Airflow** с DAG ночного сбора телеметрии.
   - В другом проекте: потоковый брокер Kafka, периодический cron-скрипт или сервис на базе Spark.
3. **Бизнес-логика эндпоинтов:**
   - Специфичные SQL-запросы, агрегации, схемы ответов (Pydantic models), отражающие предметную область (медицина, финансы, IoT, логистика).

## 3. Механизм переноса шаблона в новый проект

Процесс подключения шаблона состоит из четырех детерминированных шагов:

### Шаг 1. Перенос инфраструктурного скелета
Копируются каталоги `keycloak/`, базовая обвязка `frontend/` и модуль авторизации `auth/` из папки `api/`.

### Шаг 2. Адаптация Realm и ролевой модели
В файле `realm-template.json` при необходимости корректируются:
- имя области (`realm`);
- наименование клиента (`clientId`);
- роли приложения под доменную область (например, `operator`, `analyst`, `account_owner`).

### Шаг 3. Подключение шлюза к целевой базе
В коде бэкенда заменяется клиент подключения к СУБД. При этом декоратор безопасности остается неизменным:

```python
from fastapi import Depends, FastAPI, HTTPException, Security
from auth import get_current_user  # Готовый модуль из шаблона

app = FastAPI()

@app.get("/data")
async def get_secure_data(current_user: dict = Depends(get_current_user)):
    # 1. Извлекаем гарантированно проверенный ID владельца
    owner_id = current_user.get("preferred_username")
    
    # 2. Подставляем в запрос к НОВОЙ целевой СУБД (например, PostgreSQL)
    query = "SELECT * FROM orders WHERE customer_id = %(owner_id)s"
    
    # Выполнение запроса через драйвер целевой БД...
    return {"owner": owner_id, "data": []}

```

### Шаг 4. Настройка сетевых маршрутов в Docker Compose

Целевая база данных добавляется в общую Docker-сеть к `Reporting API`, при этом доступ к порту базы из внешней сети хоста закрывается.

## 4. Архитектурные гарантии шаблона

При переносе данного каркаса новый проект автоматически получает соответствие ключевым требованиям безопасности:

1. **Защита от перехвата учетных данных:** отсутствие передачи логинов/паролей через сторонние API (только SSO).
2. **Защита публичных клиентов:** обязательное использование OAuth 2.0 PKCE исключает атаку перехвата авторизационного кода.
3. **Автономность микросервисов:** проверка валидности токенов по открытому ключу (RS256) не создает сетевой нагрузки на Keycloak при каждом запросе.
4. **Защита от BOLA / IDOR:** физическая невозможность запроса чужих строк из подключенной СУБД за счет подстановки ID субъекта строго из полезной нагрузки токена.
