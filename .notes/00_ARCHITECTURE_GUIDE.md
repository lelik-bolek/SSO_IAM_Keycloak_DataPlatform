## 1. Главная идея и ценность проекта (Зачем я его делал)

Моя специализация — **Инженер данных (Data Engineer)**. 

**Суть этого проекта:**
Я взял классический аналитический контур (Apache Airflow + ClickHouse OLAP + FastAPI) и поместил его внутрь **защищенной инфраструктуры управления идентификацией и доступом (SSO / IAM на базе Keycloak)**.

Аналитическая витрина в ClickHouse здесь выступает **защищаемым целевым ресурсом**, а цель проекта защита инфраструктуры, в нем реализовано:
1. **Архитектурная изоляция хранения:** Вынесение отчётности из транзакционной базы в отдельный аналитический контур (ClickHouse OLAP), наполняемый пакетным оркестратором (Airflow), чтобы исключить влияние тяжёлых выборок на операционные данные.
2. **Защита от перехвата авторизации в браузере:** Настройка безопасного входа клиентского приложения (SPA) через Keycloak с использованием протокола OAuth 2.0 PKCE (S256), предотвращающего перехват авторизационного кода на стороне клиента.
3. **Защита данных от несанкционированного доступа (Zero-Trust на уровне API):** Реализация проверки JWT-токена в Reporting API и фильтрация строк в ClickHouse строго по ID из токена, что исключает просмотр чужих записей даже при ручной подмене параметров запроса.

## 2. Базовые концепции простыми словами (Словарь проекта)

### 2.1. Идентификация, Аутентификация, Авторизация
Задача безопасности — не просто «спрятать данные и никому не давать», а организовать контролируемый доступ:
1. **Идентификация:** Пользователь называет себя (например, вводит логин `prothetic1`). Система понимает, *кто* перед ней.
2. **Аутентификация:** Проверка подлинности (проверка пароля, криптографического ключа PKCE, цифровой подписи токена). Система убеждается, что пользователь — *действительно тот, за кого себя выдает*.
3. **Авторизация:** Проверка прав доступа. Система решает, *какие именно действия ему разрешены и какие строки из ClickHouse ему можно показать*.

---

### 2.2. SSO (Single Sign-On — Служба единого входа)
* **Источник:** Урок `09_sso_and_analytics` -> Раздел 1 «Основные понятия и аутентификационные протоколы».
* **Суть:** Механизм, позволяющий пользователю залогиниться **один раз** в едином окне входа и получить доступ сразу ко всем сервисам платформы (дашборд, API отчетов и др.) без повторного ввода пароля.

---

### 2.3. IAM (Identity and Access Management)
* **Источник:** Урок `09_sso_and_analytics` -> Раздел 2 «Identity and Access Management» и Раздел 5 «Выбор и настройка IAM».
* **Суть:** Единый центр управления учетными записями, группами, ролями и политиками доступа. В нашем проекте роль IAM-сервера выполняет **Keycloak**.
* **Из чего состоит инфраструктура IAM для дата-инженера:**
  1. **Каталог учетных записей (IdP — Identity Provider):** Сервер Keycloak, где внутри изолированной области (**Realm** `reports-realm`) живут пользователи, их пароли и роли.
  2. **Токены доступа (JWT / Bearer Token):** Цифровой пропуск в формате JSON, подписанный криптографическим ключом. Внутри зашиты ID пользователя (`sub`), его логин (`preferred_username`), роли и время жизни (`exp`).
  3. **Модели разграничения доступа (RBAC и ABAC):**
     - **RBAC (Role-Based Access Control):** Доступ по ролям (например, роль `prothetic_user` имеет право запрашивать отчеты).
     - **ABAC (Attribute-Based Access Control):** Доступ по атрибутам/свойствам. В нашем случае — пользователь может прочитать из таблицы ClickHouse *только те записи*, где атрибут `user_id` совпадает с его собственным ID из токена.
  4. **Ресурсный сервис (Reporting API):** Защищенный бэкенд-шлюз перед ClickHouse, который проверяет токен и фильтрует SQL-запрос.

## 3. Важное различие: Парадигма Zero-Trust vs Инженерные паттерны

В процессе разбора мы четко разделили общую философию и конкретные технические шаблоны (паттерны):

### 3.1. Глобальная парадигма: Zero-Trust («Нулевое доверие»)
* **Принцип:** *«Никогда не доверяй, всегда проверяй»*.
* **Старый (уязвимый) подход:** Если запрос пришел от нашего фронтенда (например, `GET /reports?user_id=123`), бэкенд слепо верил параметру `user_id=123` и шел с ним в базу. Злоумышленник менял цифру в адресной строке на `456` и скачивал чужие медицинские данные (уязвимость **BOLA / IDOR** — Broken Object Level Authorization).
* **Подход Zero-Trust:** Сервис отчетов принципиально не доверяет никаким параметрам, пришедшим от клиента, даже если клиент прошел вход. Каждый запрос проверяется криптографически, а идентификатор владельца извлекается строго из защищенного токена.

---

### 3.2. Инженерные паттерны (Как именно мы реализовали защиту)

Мы разобрали два ключевых паттерна. **Важно помнить: они НЕ взаимоисключающие («или-или»), они работают ВМЕСТЕ на разных этажах архитектуры.**

#### Паттерн № 1: JWT Claims Filtering / Token-Mediated Access (Уровень кода API и БД)
* **Источник:** Раздел 3 «OAuth 2.0 и JWT» + Практическое задание 2 (Задача 4).
* **Где живет:** Внутри нашего бэкенда `Reporting API` (`api/main.py`).
* **Что защищает:** Базу данных ClickHouse от выгрузки чужих строк.
* **Как работает по шагам:**
  1. Клиент присылает запрос `GET /reports` с заголовком `Authorization: Bearer <JWT>`.
  2. `Reporting API` берет публичный ключ Keycloak (алгоритм **RS256**) и прямо в своей памяти (без похода по сети в Keycloak!) проверяет, что токен настоящий, никем не изменен и не просрочен (`exp`).
  3. Из расшифрованной полезной нагрузки токена (`payload` / `claims`) бэкенд достает поле `sub` (или `preferred_username`).
  4. Бэкенд сам подставляет этот ID в параметризованный запрос к ClickHouse:
     ```python
     user_id = token_payload.get("preferred_username") # строго из токена!
     query = "SELECT * FROM prosthetic_reports_mart WHERE user_id = %(user_id)s"
     ```
  5. Любые попытки передать чужой `user_id` через URL просто игнорируются.

#### Паттерн № 2: BFF — Backend for Frontend (Архитектурный уровень доставки токена)
* **Источник:** Раздел 3 «Как безопасно хранить refresh token» + Задание 1 (Задача 1, схема C4).
* **Где живет:** Между браузером пользователя и внутренними микросервисами (на схеме C4 `schemas/task1_c4_identity.png`).
* **Что защищает:** Сами токены (`access_token` и `refresh_token`) от кражи внутри браузера через вредоносные JS-скрипты (XSS-атаки).
* **В чем проблема браузера:** Если React SPA кладет токены в `localStorage` или `sessionStorage`, любой подключенный зараженный скрипт может прочитать их и увести аккаунт.
* **Как работает BFF по шагам:**
  1. Браузер вообще не получает и не видит токенов Keycloak.
  2. Между браузером и системой стоит доверенный сервер-посредник — **BFF (API Gateway)**.
  3. Именно BFF общается с Keycloak по протоколу PKCE, забирает `access_token` + `refresh_token` и складывает их в свое закрытое серверное хранилище (например, Redis).
  4. Браузеру BFF выдает только безопасную сессионную куку с флагами:
     - `HttpOnly` (JavaScript в браузере не может прочитать куку — защита от XSS);
     - `Secure` (передача только по шифрованному HTTPS);
     - `SameSite=Strict` (защита от подделки запросов CSRF).
  5. Когда пользователь нажимает «Скачать отчет», браузер шлет запрос на BFF с этой кукой. BFF находит у себя в памяти соответствующий `access_token`, прикрепляет заголовок `Authorization: Bearer <JWT>` и пересылает запрос в `Reporting API`. А дальше в `Reporting API` срабатывает **Паттерн № 1 (JWT Claims Filtering)**.

> **Нюанс реализации в нашем репозитории:**
> На архитектурных схемах C4 (`schemas/`) у нас спроектирован полный промышленный контур с **BFF**. В локальном `docker-compose` для упрощения стенда React SPA ходит напрямую в `Reporting API` с Bearer-токеном в заголовке, полученным через PKCE. Это сделано специально, чтобы не усложнять контейнерную сборку лишним прокси-сервером, но на защите архитектуры (в `docs/` и на схемах) показана полная схема с BFF.

## 4. Механика OAuth 2.0 PKCE (Как мы закрыли дыру с перехватом кода)

* **Источник:** Раздел 3 «Авторизационные протоколы и стандарты: OAuth 2.0 и JWT» (подраздел «PKCE»).
* **В чем была проблема обычного Code Grant:** Публичные клиенты (React в браузере, мобильные приложения) не могут хранить секретный пароль приложения (`client_secret`), так как их код открыт всем. Когда сервер авторизации возвращает в браузер временный код (`authorization_code`), злоумышленник может его перехватить и обменять на токен.
* **Как работает защита PKCE (Proof Key for Code Exchange, метод S256):**
  1. Перед логином браузер сам генерирует случайный одноразовый секрет — **`code_verifier`** (длинная криптографическая строка) и прячет его у себя в памяти.
  2. Браузер считает от него необратимый хеш SHA-256 в кодировке Base64URL:
     $$\text{code\_challenge} = \text{BASE64URL}(\text{SHA256}(\text{code\_verifier}))$$
  3. **Шаг 1 (`/auth`):** Браузер просит форму входа и отдает Keycloak только хеш (`code_challenge`) и название метода (`code_challenge_method=S256`). Keycloak запоминает этот хеш.
  4. **Шаг 2 (`/token`):** Когда пользователь ввел пароль и получил временный `code`, браузер отправляет этот `code` обратно в Keycloak **вместе с исходным секретом `code_verifier`**.
  5. **Проверка:** Keycloak сам берет присланный `code_verifier`, пропускает через SHA-256 и сравнивает с тем хешем, который запомнил на Шаге 1. Если совпало — отдает токен.
* **Почему хакер бессилен:** Даже перехватив временный `code` и видя `code_challenge`, злоумышленник не знает исходный `code_verifier` (восстановить строку из SHA-256 невозможно). Без `code_verifier` Keycloak вернет ошибку `invalid_grant`.
* **Где это прописано у нас в коде:**
  - `keycloak/realm-export.json`: у клиента `reports-frontend` прописан обязательный атрибут `"pkce.code.challenge.method": "S256"` (принудительное требование PKCE) и `"directAccessGrantsEnabled": false` (запрет прямого входа по паролю в обход SSO).
  - `frontend/src/App.tsx`: в настройки провайдера передан параметр `pkceMethod: 'S256'`.

## 5. Трансграничная федерация (Federated Identity / Identity Broker)

* **Источник:** Раздел 4 «LDAP» + Задание 1 (Задача 1).
* **Проблема бизнеса:** Компания работает в разных странах. По законам (152-ФЗ, GDPR, HIPAA) хранить и передавать персональные и медицинские данные граждан за границу нельзя.
* **Как решено на архитектуре C4 (`schemas/task1_c4_identity.png`):**
  - В каждой стране филиала стоит свой локальный провайдер удостоверений (**Regional IdP** — Active Directory / OpenLDAP / локальный Keycloak) со своей локальной базой ПДн.
  - Наш центральный Keycloak выступает в роли **Identity Broker (брокера федерации)**.
  - Когда заходит иностранный пользователь, центральный Keycloak редиректит его на IdP его страны по протоколу **SAML 2.0** или **OIDC**.
  - Локальный IdP проверяет пользователя у себя на родине и присылает в наш центральный Keycloak только подписанное утверждение (**assertion / токен**) с обезличенным ID и группой, которую Keycloak маппит на внутреннюю роль `prothetic_user`. Сырые ПДн границу не пересекают.

## 6. Как устроен наш аналитический контур (Data Engineering часть)

1. **Источники данных (на схеме C4 `schemas/task2-report.png`):**
   - **Операционная БД телеметрии (PostgreSQL):** сюда с высокой частотой пишутся сырые данные с чипов протезов.
   - **CRM-система (с базой Oracle):** хранит справочник клиентов и привязку серийных номеров протезов к конкретным людям.
2. **Оркестратор ETL (`airflow/dags/telemetry_crm_mart_dag.py`):**
   - DAG `telemetry_crm_mart_etl` запускается по расписанию `@daily` (раз в сутки за вчерашний закрытый день).
   - Выгружает данные телеметрии и справочник CRM, объединяет (денормализует) их и делает пакетную вставку (**Batch INSERT**) в ClickHouse.
3. **Аналитическое хранилище (`clickhouse/init_mart.sql`):**
   - Колоночная СУБД **ClickHouse**, таблица-витрина `prosthetic_reports_mart` на движке `MergeTree()`.
   - Таблица широкая и денормализованная (по Кимбаллу) — никаких тяжелых `JOIN` во время пользовательского запроса.
   - Ключ сортировки: `ORDER BY (user_id, report_date)`. Благодаря этому все данные одного пользователя лежат на диске подряд, и выборка `WHERE user_id = ...` выполняется мгновенно.
4. **Сервис выдачи отчетов (`api/main.py`):**
   - Микросервис на **FastAPI**, эндпоинт `GET /reports`.
   - Проверяет JWT-токен (RS256), достает `user_id` из токена, делает быстрый `SELECT` из готовой витрины ClickHouse и проверяет, не запросил ли пользователь сегодняшний (еще не обработанный Airflow) день.

## 7. Сквозной путь данных и запросов (Шпаргалка «Как всё работает в связке»)

1. **Фоновый процесс (ночью):**
   `Airflow` $\rightarrow$ собирает данные за вчерашний день $\rightarrow$ делает `Batch INSERT` в витрину `ClickHouse` (`prosthetic_reports_mart`).
2. **Вход пользователя (утром):**
   Пользователь открывает `React SPA (порт 3000)` $\rightarrow$ редирект в `Keycloak (порт 8080)` с `code_challenge (S256)` $\rightarrow$ ввод логина/пароля $\rightarrow$ обмен кода + `code_verifier` на `JWT-токен (RS256)`.
3. **Запрос отчета:**
   Пользователь жмет «Download Report» $\rightarrow$ запрос идет в `Reporting API (порт 8000)` с заголовком `Bearer <JWT>` $\rightarrow$ API проверяет подпись токена публичным ключом Keycloak $\rightarrow$ забирает `user_id` прямо из токена $\rightarrow$ выполняет `SELECT ... WHERE user_id = :token_user_id` в `ClickHouse (порт 8123)` $\rightarrow$ возвращает пользователю строго его строки.
